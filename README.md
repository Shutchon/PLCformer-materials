# PLCformer Materials

Computational materials for **constructive neural compilation of bounded programmable logic controller programs**. This repository contains the implementation, control programs, synthetic inputs, tensor checkpoints, tests, and recorded results. It is intended as the repository accompanying the research article; the manuscript itself is not included.

**Version 1.1.0:** one consolidated supplementary package, including the external production-line case. Start here after extracting `PLCformer-materials-v1.1.0.zip`; a GitHub account and the main project repository are not required.

**Authors:** Shutchon Premchaisawatt, Krit Tashoo, and Narong Boonsaner.

## Quick start

Use Python 3.10 or later; the recorded environment used Python 3.10.11. From the root of a downloaded or cloned copy of this repository:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python examples/self_hold.py
python -m pytest -q
```

On Windows PowerShell, activate with `.venv\Scripts\Activate.ps1`. Run all subsequent commands from the repository root with that environment active.

The example prints five scans with motor outputs `0, 1, 1, 0, 0`, checking eager and sparse execution against the expected start/hold/stop behavior. The supplied test suite has 51 tests.

`requirements.txt` lists the required packages. `requirements-repro.txt` records the exact top-level versions used for the reference run: PyTorch 2.14.1, NumPy 2.2.6, Numba 0.68.1, pytest 9.2.0, and safetensors 0.8.0. It is an environment record, not a portable lockfile; package availability depends on Python and platform. Neither LaTeX nor Transformers is needed.

## Inspect the supplied materials without rerunning experiments

```bash
# Standard-library-only verification of reference source and artifact checksums.
python tools/verify_artifacts.py

# Export a readable report and eleven CSV files from the reference results.
python tools/summarize_results.py
```

The report is written to `results/local/summary/SUMMARY.md`; CSVs cover state agreement, CPU throughput, controller batches, latency, gate error, scalar-fitting history, and the external case (transitions, closed loop, fixtures, median timings and all 54 repeat durations). The untouched reference measurements remain in `results/reference/`.

The reference run checks **400,000 scans** across four synthetic workloads with zero process-image/stack mismatches after normalization. It also checks 500 eager scans per workload, all 16 binary interlock patterns, and 10,000 synthetic proposals. Full numerical values and environment metadata are supplied in JSON.

## Reproduce the four-workload evaluation

```bash
python -m benchmarks.run_all_experiments
python tools/summarize_results.py --input benchmarks --output results/local/rerun-summary
```

The runner performs these experiments in order:

1. State comparisons: 100,000 scans for each of the four bundled programs.
2. Repeated throughput measurements: eager PyTorch, Python reference, neural Numba, and direct integer Numba, plus Boolean controller batches.
3. Interlock checks and independent scalar sigmoid fitting.
4. Raw gate-error ablation and empirical scan-kernel latency.

It overwrites **`benchmarks/results_summary.json` and `benchmarks/ablation_results.json`**, preserving the supplied snapshots under `results/reference/`. The original evaluation took approximately one minute on the recorded Apple M5, excluding first-time compilation. Other machines may take longer. Numba compilation is warmed up before throughput measurement. MPS is used for Boolean batches when available; otherwise the runner records CPU fallback. CUDA batching is not implemented by this runner.

The reference machine had an Apple M5, 32 GiB memory, 10 logical CPU cores, and four PyTorch CPU threads. New timings should be reported with the environment generated by the runner. Exact throughput is not an expected reproducibility invariant.

After a rerun, package inventory verification will identify the two changed working result files. This is expected: `MATERIALS_MANIFEST.json` describes the distributed snapshot. To verify an untouched release, use a fresh checkout. Source hashes in `results/reference/results_summary.json` still identify the implementation used for the reference run.

## Reproduce the external production-line case

The [case protocol](benchmarks/production_line_case/README.md) describes how to
obtain and build matiec at its pinned revision. Build tools and the native oracle
are required for the independent-compiler checks; they are not required just to
inspect results, verify checksums or run the Python test suite.

After building matiec at `/tmp/matiec`, run from this repository root:

```bash
python -m benchmarks.production_line_case.build_oracle --matiec-root /tmp/matiec
mkdir -p results/local
python -m benchmarks.production_line_case.run \
  --oracle benchmarks/local/production_line_oracle/oracle.so \
  --devices cpu,mps --output results/local/production_line_results.json
```

Use `--devices cpu` on machines without Apple MPS; add `--validation-only` to
skip timing. The native build workflow was tested on macOS with Clang, flex,
autoconf, automake and bison >=2.4. It is not a tested Windows build recipe.
Run timing without concurrent tests or other benchmark jobs. The four-workload
runner above does not run this separate experiment automatically.

The immutable reference is `results/reference/production_line_results.json`.
Each measured backend agrees with matiec on **32,768 canonical transitions**
and **8,192 synthetic closed-loop scans**, with 224 completed parts. All 20
original fixture scans agree between matiec and PLCformer; two disagree with
the supplied expectations when omitted initial state is filled with zeros.
An explicitly completed fixture and a manual-to-automatic reverse-retention
counterexample are reported separately. PLCformer is slower than native C and
direct tensor execution at every measured device/batch pair. The external
controller is manually lowered; this is not general ST/CASE support or physical
plant validation. The upstream Apache-2.0 source, license and attribution are
included under `benchmarks/external/agents4plc/`; matiec is obtained separately.

See [docs/RESULTS_MAP.md](docs/RESULTS_MAP.md) for the files and commands behind
each reported experiment. Source/result checksums link the original and external
experiments to the same unchanged core implementation.

## Use the synthetic inputs

```python
import numpy as np

with np.load("data/self_hold.npz", allow_pickle=False) as data:
    inputs = data["inputs"]  # (100000, 16), float32; columns X0..X15
    print(inputs.shape, int(data["seed"]), int(data["scan_ticks"]))
```

The four seeds are 42 (self-hold), 43 (star–delta), 44 (traffic lights), and 45 (sorting). Programs are stored in `benchmarks/programs/`. Inputs are synthetic and contain no field measurements or private datasets.

Regenerate the input schedules and checkpoints into a separate directory:

```bash
python tools/export_materials.py --output results/local/export
```

This writes four `.npz` input schedules, four `.safetensors` checkpoints, and their manifest. Each checkpoint contains constructive weights and initial state for its program; it is an inspection/export artifact, not a stock language-model checkpoint.

## Run another supported program

```python
from runtime.host import PLCformerHost
from runtime.fast_engine import FastNumbaEngine

host = PLCformerHost("LD X0\nTON T0, K5\nOUT Y0\nEND")
for _ in range(6):
    result = host.run_scan_cycle({"X0": 1})
    print(result.outputs_y["Y0"])

# Create the sparse engine from a fresh host for an independent run.
fast = FastNumbaEngine(PLCformerHost("LD X0\nOUT Y0\nEND"))
fast.run_scan_cycle({"X0": 1})
print(fast.read_bit("Y0"))
```

`host.load_program_file(path)` loads a PLC-IR file. `PLCformerHost(source, is_structured_text=True)` accepts the documented restricted ST-like syntax. `host.run_scan_cycle(inputs, mode="mode_b")` uses Boolean unrolling when supported; general stateful/word programs fall back to the instruction interpreter.

The numeric domain is signed 16-bit-range integers, with nonnegative timer/counter presets, integer scan ticks, at most 256 instructions including END, and a balanced eight-entry stack. Overflow raises an exception. No physical I/O or certified fault response is implemented.

## Interpretation and limitations

This is a custom bounded controller runtime, not a full IEC 61131-3 implementation or a stock Qwen model. Differential agreement is measured after numeric normalization, not a proof of raw float32 exactness for all programs. The direct integer baseline outperforms neural execution on these standalone workloads. Batched amortized cost is not an individual controller's response latency; measured percentiles are not WCET bounds.

The interlock experiment uses synthetic commands, not LLM outputs. Scalar sigmoid fitting is separate from the compiled controller. No physical-plant deployment, safety certification, or language-model integration is demonstrated.

See [artifact details and attribution](docs/ARTIFACTS.md). When citing this package, use `CITATION.cff` and record the exact release tag or commit so that the source and measurements remain identifiable.
